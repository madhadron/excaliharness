# Excaliharness

Copyright 2026 Frederick Ross.

A VS Code extension for agentic coding with Claude:
- humans make cross cutting decisions up front
- every decision and task lives in Markdown in the repository
- and agents hand back work in small units that are ready to review

(This README.md was generated by Claude and lightly edited by a human.)

# Requirements

- Visual Studio Code
- [Docker](https://www.docker.com/) (Engine 26 or later, such as a current Docker Desktop)
- a Claude account

# Context

Excaliharness is a standalone VS Code extension. It consists of a subprocess (the orchestrator) that runs
agents, and the extension itself that adds functionality to VSCode.

It is early work. Task files, statuses, sign-in and the review loop (the
implementer, the required gates and reviewer agents, for up to three rounds)
work today. The design step for UI work and the in-editor review UI come after
that ([docs/roadmap.md](docs/roadmap.md)).

The design follows a few principles:

* **The human decides, early.** Cross-cutting choices (stack, libraries, APIs,
  data model, UI text) are made by the human and recorded in
  `docs/decisions.md` before agents build on them. Every agent gets those
  decisions as context and must follow them. When it hits a decision they
  don't cover, it asks a question in the task file and waits instead of
  guessing.
* **Everything lives in Markdown, in git.** Tasks, decisions, agent
  definitions and pipelines are plain files in the repository. They are the
  only source of truth: you can read and edit all of them, and every change is
  a diff you can review.
* **Work arrives in units sized for review.** Each task runs on its own branch
  and worktree. The human sees a task only once it passes the project's
  required checks and reviewer agents with nothing left open, nits included,
  or after three rounds with what's left listed.
* **Agents get only what they need.** Agents run in locked-down containers
  that can't reach the internet. A small proxy holds the Claude token and
  forwards only Claude API requests, so an agent never sees the token. Git
  runs only on the host, and agents can't change task files or decisions.
  Images are built locally from pinned sources and never pulled by name.
  Excaliharness expects a Dockerfile and compose.yaml file in the root of
  the repository.
* **The project documents its own commands.** Each repository lists its
  commands in its README's "Quick reference". The ones marked
  `(required gate)` are the checks agents' work must pass. Excaliharness
  reads that to learn how to work with the project.
* **Every reference is a link, and every capability is discoverable.** Tasks
  link to their dependencies, agents and reviews. Everything the extension can
  do has a CodeLens, command, hover or button where you are working, rather
  than a file format or command name you have to remember.

The reasoning behind each choice is in [docs/decisions.md](docs/decisions.md).

# How it works

Here is an example of working on a project with Excaliharness.

1. **Set up the repository.** Open it in VS Code with the extension installed.
   Excaliharness expects:
   * a `Dockerfile` and Compose file at the root, where the service built from
     that Dockerfile is the dev environment agents work in;
   * a `README.md` with a `# Quick reference` section listing the project's
     commands, with the required gates marked;
   * `TASKS.md`, which indexes the tasks and names the pipelines (which agents
     implement and which review);
   * the agents themselves in `agents/*.md`, in the Claude Code subagent
     format.

   For a new project, the first tasks are the infrastructure tasks that create
   these files.
2. **Decide.** Write the cross-cutting decisions into `docs/decisions.md`:
   language, framework, how errors are reported. Agents read this file before
   every round.
3. **Write tasks.** Each task is a file `tasks/T-NNN.md` with a description,
   its context, the issue, the expected outcome, and links to the tasks it
   depends on ([docs/task-format.md](docs/task-format.md)). New tasks start
   as `draft`, and nothing touches a draft. `[[T-NNN]]` links can be
   followed, and problems in a file show in the Problems panel.
4. **Mark it ready.** A CodeLens above the status line offers "Mark ready".
   The orchestrator keeps the task waiting until its dependencies are done
   and keeps the `TASKS.md` index up to date.
5. **Sign in once.** The first time a task needs Claude, the extension asks
   you to sign in. The sign-in runs in a container, and the token is kept in
   VS Code's secret storage. The status bar shows your account.
6. **The task runs.** The orchestrator:
   * creates the task's worktree and branch;
   * builds the agent image from your dev image;
   * starts your project's services with locked-down settings;
   * checks that the image has what agents need;
   * runs the implementer agent and commits its changes.

   Progress and the agent's summary appear in the task's `## Updates`. Up to
   two tasks run at once, which the `excaliharness.maxParallelTasks` setting
   controls.
7. **Checks and reviews.** After the implementer, the required gates
   run on the commit, then the reviewer agents look at the diff. Failures and
   findings go back to the implementer for another round, until nothing is
   left or three rounds have passed. If the implementer changes the
   Dockerfile or a dependency file, the task stops for you to approve
   rebuilding the image with network access.
8. **Answer questions.** If an agent needs a decision you haven't made, it
   adds a question under `## Questions` and the task becomes
   `needs-decision`, and you get a notification. Write your answer and check
   the box, and the task picks up where it stopped.
9. **Review.** When a task is ready, VS Code shows a notification, spoken
   too, with "Open review". The same link is added to the task's metadata
   (`* review: [Open review](vscode://madhadron.excaliharness/review/T-NNN)`),
   and an "Open review" CodeLens appears above its status line and on its
   `TASKS.md` entry. Each opens the task's worktree in a new window that
   VS Code doesn't trust, so its tasks and workspace settings stay off. That
   window shows the branch's changes against the commit where it left your
   branch, and you can edit there directly. Line comments, chat and an
   Approve button that merges the branch come with the review UI. When you're satisfied, mark the task done, and
   the tasks waiting on it start.

If you set a status by hand that the orchestrator should set, the task is
*parked*: nothing more happens to it until you mark it ready or move it back
to draft. A CodeLens offers both.

# Quick reference

```
# Run type checking (required gate)
make typecheck
# Run lint (required gate)
make lint
# Run unit tests (required gate)
make test-unit
# Run VS Code integration tests (required gate)
make test-vscode
# Build the base agent image (required gate)
make agent-image

# Run every gate
make check
# Build the extension into dist/
make build
# Package the extension as a .vsix
make package
# Open a shell in the dev container
make shell
```

Development needs only Docker and VS Code on the host. Everything else runs in
the dev container defined in `Dockerfile` and `docker-compose.yml`. To try the
extension, press F5 in VS Code: it builds in the container and opens an
Extension Development Host on a fixture workspace. To install it, run
`make package` and install the `.vsix` from `dist/` with "Extensions: Install
from VSIX…".

# Repository layout

The repository holds one VS Code extension, which contains the orchestrator,
plus everything needed to build, test and steer it. The code splits into the
extension (the UI side, running in VS Code's extension host) and the
orchestrator worker (a child process it starts), with two kinds of tests. The
Markdown under `docs/` is how humans and agents share context: agents read it
before working, and humans record decisions there. The build and test
infrastructure is all containers, so the host needs only Docker and VS Code.

* Source code (`src/`), bundled by esbuild into `dist/`
    * Extension: `src/extension.ts` (entry point) and the modules it wires up:
      `workerClient.ts` (starts, talks to and restarts the worker),
      `taskState.ts` (latest task snapshot), `links.ts` (wikilinks),
      `diagnostics.ts` (Problems panel), `statusLens.ts` and `commands.ts`
      (Mark ready / Mark done / Back to draft), `auth.ts` (Claude sign-in and
      the token), `editorText.ts` (pure text helpers)
    * Orchestrator worker: `src/worker/`, with `main.ts` as its entry point
        * `protocol.ts`: messages exchanged with the extension
        * `orchestrator.ts`: scans, applies status rules, writes, notifies,
          and starts tasks
        * `store.ts`, `watch.ts`, `lock.ts`, `git.ts`: safe writes, file
          watching, the one-window-per-repo lock, reading git state
        * `docker.ts`, `agentImage.ts`, `signIn.ts`: the Docker Engine client,
          building the images the extension ships, and Claude sign-in
        * `runner/`: running tasks
            * `scheduler.ts`, `runner.ts`: which tasks run, and one round of
              a task
            * `compose.ts`, `yaml.ts`, `project.ts`: reading the target's
              Compose setup, the locked-down override, and the task's
              Compose project
            * `images.ts`, `capability.ts`: the dev and derived agent images,
              and checking them
            * `worktree.ts`: task worktrees (kept in the extension's storage)
              and host-side commits
            * `session.ts`, `prompts.ts`: the agent's session through the
              Agent SDK, and what it is told
            * `exec.ts`, `clean.ts`, `errors.ts`: running commands, cleaning
              agent-written text, and the errors the orchestrator handles
        * `proxy/`: the egress proxy that holds the token
        * `agents/`: reading agent definitions
        * `tasks/`: the task file model, parser, edits, status rules, index
          and the README Quick reference
* Unit tests: `*.test.ts` next to the code they test (for example
  `src/worker/protocol.test.ts`), run by Vitest without VS Code
* VS Code integration tests: `src/test/`, run by `@vscode/test-cli` in a real,
  headless VS Code
    * `src/test/*.test.ts`: the tests
    * `src/test/fixtures/workspace/`: the workspace they open
* Context shared by humans and agents
    * `docs/decisions.md`: approved decisions; agents must follow them
    * `docs/task-format.md`: the task file and `TASKS.md` formats
    * `docs/experiments.md`: experiment results that decisions rely on
    * `docs/roadmap.md`: agreed future work and open security constraints
    * `CLAUDE.md`: working rules for Claude sessions in this repository
    * This README's Quick reference: the commands used to do development
      tasks in this repository. Those marked as required gates must be run
      by all agents generating code and pass before the code is accepted.
* Build and test infrastructure
    * `Dockerfile`, `docker-compose.yml`: the dev container
    * `agent-image/`: the base agent image, with the pinned Claude Code
      binary, used for sign-in and for infrastructure tasks before a target
      repo has a dev image. Other tasks run in an image derived from the
      target's own dev image (D-064). `agent-image/proxy/` is the egress
      proxy's image (D-066)
    * `Makefile`: the commands in the Quick reference
    * `package.json`, `package-lock.json`: dependencies and npm scripts
    * `esbuild.mjs`, `tsconfig.json`, `eslint.config.mjs`, `vitest.config.mts`,
      `.vscode-test.mjs`: build, type-check, lint and test configuration
    * `.vscode/`: F5 launch and build task for debugging the extension
* Experiments: `experiments/`, throwaway code behind `docs/experiments.md`
    * `setup-token/`, `sign-in-smoke/`: Claude sign-in in a container
      (E-001 to E-004)
    * `compose-override/`: the Compose override and the token-holding proxy
      (E-005 to E-007)
    * `runner-smoke/`: the agent runner against a stand-in target repo, with
      a fake token or, through `real-token.sh`, a real one (E-009)
